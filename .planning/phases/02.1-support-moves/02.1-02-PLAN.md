<objective>
Give the 技クリエーター (`src/creator.tpl.html`) a way to author the `kind`/`effect` fields Plan 01
made meaningful in battle: an 攻撃/補助 toggle, effect inputs (stat/delta/dur/target) that only
appear for 補助, and a hidden-when-補助 威力 slider. Wire these through every place a custom move
object is created, copied, synced into the runtime `MOVES` table, and saved to/loaded from the
shared library shelf.

Purpose: without this, `kind:'support'` can only ever be set by hand-editing JSON — にーくら has no
way to actually author a support move. This is design doc §4.5-4, item 5 of 6.

Output: a working 補助技 authoring flow in the creator, and `tools/verify_creator.js` extended to
prove the round-trip.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| 技クリエーターの効果入力 → 技棚保存 | The new stat/delta/dur/target inputs are the only UI-driven path that can now write an `effect` block; a user could still bypass the UI's -25..25/3..20 slider ranges via `$('mvJsonLoad')`'s raw JSON paste, same boundary as Plan 01's T-02.1-01 |
| 技棚 (shioumon_move_lib_v1) → 他個体の customMoves | Loading a shelf record into a monster's `customMoves[]` trusts `rec.battle.kind`/`rec.battle.effect` without re-validating range, same as any other shelf field (power/cast/cooldown already have no server-side validation either — consistent with existing project posture) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02.1-05 | Tampering | `load(rec,k)` flattening `rec.battle.effect` from an arbitrary shelf record onto a live `customMoves[]` entry with no range re-validation | low | accept | Plan 01's `applySupportEffect`/`statOf` already clamp/whitelist at the point of battle-effect (T-02.1-01) regardless of how the data arrived — this UI layer inherits that downstream mitigation, so no duplicate validation is required here; consistent with how `power`/`cast`/`cooldown` are already handled (no UI-layer re-validation, downstream math bounds the impact) |
| T-02.1-SC | Tampering (supply chain) | npm/pip/cargo installs | n/a | n/a | No new package-manager dependencies introduced by this plan |
