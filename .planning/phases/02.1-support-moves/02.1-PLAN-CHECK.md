### 2. B3 の新式は、**16通り全部で符号が正しい**

`net = ΔflowToFoe/foe.maxHP − ΔflowToF/f.maxHP` を仕様どおり実装して総当たりした

### 5. 改訂で**新しく入った穴** —— ここが今回の BLOCKER 2件

#### R1 [BLOCKER] 較正シナリオの前提が**1つも固定されとらん**。ページの既定は全50やない

`02.1-01` Task 2 の較正も、Task 1 の「byte-identical な数値サンプル」も、
**「default (all-50) stats、`maxHP=120` 両者」**を前提に書かれとる。
しかし `resetBattle()` は `ally=partyA[0]; enemy=partyB[0];` を復元し、その中身は:

| | 実際の既定 | 計画の前提 |
|---|---|---|
| `ally` = パルキア | atk92 def78 hp70 spd80 eva62 **int88** / per aggr62 caut52 loyal32 self44 | 全て50 |
| `enemy` = ルギアもどき | atk64 def58 hp60 spd38 eva35 int45 | 全て50 |
| `maxHP` | 152 / 136 | 120 / 120 |
| softmax 温度 `T` | `1.2+(100-88)*0.34` = **5.28** | 18.2 |

そのままでは、この3つが順位比較を汚す:

1. **性格項（P）が生きる。** パルキアは per が50から外れとるけん
   `P("好戦", dmgV*0.6*dAg + castV*-0.55*dAg)` が発火する。`dmgV=0` の補助技と攻撃技で
   効き方が違う。全50なら P は全部消える。
2. **`f.side==="ally"` の作戦項が乗る。** `TACTIC_BIAS[panel.tactic]` は `dr`（補助技では0）を
   引数に取るけん、補助技に不利な向きへ傾く。`f` を `enemy` 側にすれば丸ごと消える。
3. **`foeBusy` の作り方。** 計画は「`foe.charging` を非 null にする」と書いとるが、
   `scoreMove` には `if(foe.charging && cast<foe.charging.t) R("割り込み", 26)` がある。
   `charging.t` の置き方次第で**攻撃技だけに +26×read が乗る**（例: `t=0.35` なら攻撃だけ +13 →
   35.3 対 32.87 で**順位が逆転して assert が落ちる**）。`foe.actionTimer=1.0` で `foeBusy` を
   真にすれば `割り込み` は絶対に発火せん。

さらに **Task 1 手順5 に実害のある1行**がある:

> temporarily set `f.stats.atk=150` … **Restore `f.stats.atk` to 50 afterward.**

パルキアの atk は **92** や。50 に「戻す」と**個体を壊したまま**後続の検査
（Task 2 の順位比較・Task 3・`02.1-03` の `determinismTest`）へ持ち越す。
`determinismTest` は2回とも同じ壊れ方をするけん **緑のまま気付けん**。

**直し方（全部 plan の文言だけ）**: 較正シナリオの先頭で
`f`（`enemy` 側を推奨）と `foe` の **6 stats を50、4 per を50に固定**し、
`foeBusy` は `foe.actionTimer=1.0` で作り、
一時変更は `try/finally` で**元の値を保存して戻す**（「50 に戻す」と書かん）。

#### R2 [BLOCKER] `buffValue` が `statOf` の **1〜100 の天井を勘定に入れとらん**

`statOf` は `Math.max(1, Math.min(100, Math.round(v)))` で丸める（Task 1 手順2、canon どおり）。
ところが `rawFlow` の仕様は `delta` を素のまま足す（`0.5+attackerAtk/100`）。
**にーくらの既定ロスターは高ステータス**やけん、これが日常的に効く:

パルキア（atk **92**）に `atk+25` を掛けても、実際に効くんは `statOf` が返す 100 まで＝**+8**。
なのに `buffValue` は +25 ぶんを値踏みする:

| | 補助の値打ち | 補助技の合計 | 攻撃（灼熱弾） | 順位 |
|---|---|---|---|---|
| 天井を勘定に入れん（＝計画の仕様どおり） | **40.56** | 42.80 | 32.91 | 補助が勝つ |
| 天井を勘定に入れる（＝実際に起きること） | **12.98** | 15.22 | 32.91 | 補助が負ける |

**3.1倍の過大評価**や。しかも既定ロスターは atk92 / def80 / eva84 / spd88 と、
6体中3体が **75 を超えとる**（+25 が全部は入らん個体）。結果:

- AI は**ほとんど効かん補助技を、効くと思って優先する**
- **AIログが 40.6 と表示して 13.0 しか出さん** —— 掟9（内訳が見えん実装をしない）に真正面から反する
- R1 と重なると最悪で、**executor が正しく天井を実装したら順位 assert が落ち**、
  その場の直し方として `SUPPORT_W.scale` を上げたくなる —— 計画が正しく拒んだ手が復活する

**直し方**: `rawFlow` の中で `statOf` と同じ丸めを通すだけ。
`const eff = Math.max(1, Math.min(100, Math.round(base + delta)));` として
`delta_eff = eff - base` で計算する。2行。`def`/`spd`/`eva` の枝も同じ扱いにする
（`eva` は `tryDodge` 側で `prob` が `[0.02,0.95]` に丸められるけん同じ性質を持つ）。

### 6. 残置の判断（projectile/beam の補助技が「前へ突き出す」構えになる）—— **出してよい**

`MOVE_RANGE.motionOf(move)` は `MOTION[rangeOf(move)]` を返すだけで `kind` を見とらん。
`rangeOf` は `move.range` → 無ければ generator。`syncCustom()` の作る runtime エントリに
`range` は入らんけん、自作技は必ず generator 由来になる。よって残置は本物や。**ただし:**

- 補助技の自然な素材は `aura`（→ remote → `charge`）で、**そこは最初から正しい**
- **`fx.motions[]` を書けば分類の既定に勝つ**（`scheduleMotions` の先頭で分岐）。
  制作ツールは `mlMotions($("mvMotion"),mvCtx)` でその入力を**既に出しとる** ——
  作者側に逃げ道がある
- 直すなら `motionOf` に `kind` を渡す形になるが、そこは `verify_look.js` の
  KEEP-01/02 が見張る共有の既定モーションで、このフェーズで触る値打ちが薄い

**既知の制限として文書化のうえ出荷でよい。** Phase 3 で aura 3本を作り直すときに
`motionOf(move, kind)` を検討する、で足りる。
