# Phase 1（反動と間）: 状態を分ける Verification Report

**Phase Goal:** 今どの状態に居るかが1つの値で読めて、ログに残る
**Status:** passed
**Requirements:** STATE-01, STATE-02, STATE-03, VER-02, VER-03

## 発端

にーくらの指摘:

> **CD（反動）は、攻撃したくてもできない状態**で、
> **間は、攻撃できるが、回避などを行えるように……攻撃せず、様子見などをしている状態**を間だ。

**この2つは区別されとらんかった。** 状態は3箇所に散らばっとった:

```
f.charging      溜め中か
f.cd[m.id]      技ごとのクールダウン
f.actionTimer   次の行動までの時間
```

「反動中か」を知るには全部を見る必要があって、しかも `actionTimer` は
**撃てるのに待っとるだけの時間も含む**けん、それ単体では判定に使えん。

## 成功基準ごとの結果

### 1. 状態が1つの値で取れる — ✓ 通過

```
charge=溜め / down=戦闘不能 / free=自由 / hold=間 / recoil=反動
```

判定の順序に意味がある:

```
戦闘不能  すべてに勝つ
溜め      反動より先に見る —— 溜めながら次が撃てん状態は「溜め」やけん
反動      撃てる技が1本も無い
間        撃てるのに撃たん（Phase 2 で AI が立てる）
自由      撃てて、撃つ気がある
```

**`actionTimer` では判定しとらん。** あれは「撃てるのに待っとる時間」も含むけん、
反動と混ざる。混ぜたら、にーくらが分けたがっとる2つがまた1つに戻る。

### 2. 実際に条件を作って読めるか — ✓ 通過

作り物の状態を5通り立てて、全部期待どおりに返った:

```
全部撃てる            → free
全技クールダウン中    → recoil
溜め中かつ全技CD中    → charge（溜めが勝つ）
holding を立てた      → hold
戦闘不能             → down（すべてに勝つ）
```

### 3. 実戦で反動が本当に起きるか — ✓ 通過

3分ぶん回した実測:

```
free 3591 / charge 711 / recoil 675 / down 217   （フレーム数）
構えのログ 23件
例: いわもどき：自由 → 反動（技が全部クールダウン中／最短 1.4s）
```

**反動は作り物やのうて実戦で起きとる**（675フレーム分）。
`hold` は **0件** —— まだ誰も間を選ばんけん正しい。Phase 2 で初めて出る。

ログは **23件**。毎フレーム出しとったら数千件になって、肝心の判断が読めんくなる。
**状態が変わった瞬間だけ**出しとる。

### 4. 挙動が1ミリも変わっとらん — ✓ 通過（Phase 1 の本題）

このフェーズの約束は「読めるようにするだけ」やけん、
**何も変わっとらんことの方が本題**や。

```
determinismTest()        ok
同じ種で2回走らせて一致  true（4151フレーム・全滅）
```

`determinismTest` は HP しか見とらんけん、**経済と決着も突き合わせた** ——
フレーム数・決着理由・クォーター・両陣営の所持コスト・全個体のHP、全部一致。

`noteStance(f)` は `stepFighter` の中で呼んどるが、**戻り値を判断に使っとらん**。
使った瞬間にこの約束が破れる。
