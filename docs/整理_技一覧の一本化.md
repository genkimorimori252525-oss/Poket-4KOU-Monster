## 1. 今の形と、何が問題か

```
docs/技ネタ_タイプ別.md   180個のネタ（文書・タイプ別10個ずつ）
        ↓ 手で起こす
src/starter_moves.js       52本（コード。/*__STARTER__*/ で dist へ焼き込まれる）
        ↓「ネタ帳の技を棚に入れる」ボタン
data/moves/library.json    54本（= 上の52本 ＋ 亜空切断・灼熱弾）
        ↓
creator「■ 覚える技（最大4つ）」
```

**同じ52本が2箇所にある**（名前が1本残らず一致することを確認済み）。
片方を直しても、もう片方が古いまま残る。38本を作り直すと、この二重管理が38本ぶん効いてくる。

さらに、180個のネタのうち**実装されとるのは52個だけ**。残り128個は文書の中にしか無い。

## 2. ⚠ 素直に一本化すると掟を破る

`src/store_bridge.js` は **`file://` で丸ごと何もせずに抜ける**：

```js
/* file:// 直開きなら何もせん */
if (location.protocol !== 'http:' && location.protocol !== 'https:') { bail(...); return; }
```

つまり `data/moves/library.json` が効くんは **`npm run dev` でサーバー越しに開いたときだけ**。
`dist/*.html` を直接開いたとき技が存在しとるのは、`starter_moves.js` が
`build.js` の `/*__STARTER__*/` で**焼き込まれとる**から。

**`starter_moves.js` を消して library.json だけにすると、`dist/` 単体で技が0本になる。**
掟「`dist/` は単体で開ける・外部参照ゼロ」と正面衝突する。

### 抜け道：`starter_moves.js` を「生成物」にする

正は `library.json` ひとつ。`build.js` がそこから読んで焼き込む。

```
data/moves/library.json   ← 正。人が触るのはここだけ
        ↓ build.js が生成（手で書かん）
   /*__STARTER__*/ の中身   ← dist に焼き込まれる。単体で開ける（掟を守る）
```

`build.js` の該当行を差し替えるだけで済む：

```js
/* 今 */
'/*__STARTER__*/' : read('starter_moves.js'),
/* あと */
'/*__STARTER__*/' : genStarter(),   // data/moves/library.json から組み立てる
```

**`src/starter_moves.js` は削除する。** 生成物をファイルに落とす必要が無い
（`build.js` が文字列を組んでそのまま差し込むけん）。
これで二重管理が**構造的に**消える —— 手で同期する余地が無くなる。

## 3. 技一覧のレコードに足すもの

`library.json` は今 `{ 技名: {name, fx, battle, audio} }`。ここに2つ足す。

```jsonc
"はっぱカッター": {
  "name": "はっぱカッター",
  "fx": { ... }, "battle": { ... }, "audio": [ ... ],

  "status": "made",        // ★足す: made（作った） / idea（ネタのまま） / retired（使わん）
  "note": "作り直し待ち"    // ★足す: 任意。一覧で理由が読めるように
}
```

### `status` が要る理由

技ネタ帳を廃止して180個を技一覧へ移すと、**128個は fx を持っとらん**。
そのまま焼き込むと絵の出ん技が棚に並ぶ。`status` で分ける：

| status | 意味 | `dist` へ焼き込む | 棚（覚える候補）に出す |
|---|---|---|---|
| `made` | 演出まで仕上がっとる | **する** | **する** |
| `idea` | ネタ帳から移しただけ。`fx` は無い | せん | せん |
| `retired` | 作ったが使わんことにした | せん | せん |

`status` を書いとらん技は `made` 扱い（後方互換。今の54本は1つも触らんで済む）。

### 128個のネタを入れる（決定・2026-08-20）

にーくら「技一覧に入れるべき。だってそうだろ？」——**入れる。** 実測したら安かった：

| | |
|---|---|
| `fx` 無しのネタ1本 | **約132 bytes**（name + battle + status だけ） |
| 128個ぜんぶ足して | **約17 KB** |
| 今の `dist/shioumon_creator.html` | 947 KB → **増えるんは 1.8%** |
| （参考）128個ぜんぶ仕上げたら | 約118 KB 増。ただし**作ったぶんだけ**増える |

`fx` を持っとらんけん軽い。仕上がるにつれて増えるが、それは仕事が進んだぶんやけん妥当。

### 軽量化について（にーくらの案は、既にそうなっとった）

にーくら「実戦では、トレーナーが組み合わせて選んだ技しか読み込まれないようにすれば、
1四皇モンが128以上の技を持っているような惨事は防げるだろ？」

**その形に既になっとる。** 数えて確かめた：

| テンプレ | `/*__STARTER__*/`（技の棚）が入っとるか |
|---|---|
| `creator.tpl.html` | **入っとる**（1件） |
| `battle.tpl.html` | **0件** |
| `lab.tpl.html` | 0件 |
| `audiolab.tpl.html` | 0件 |

戦闘が技を得る経路は**個体データそのもの**（`src/roster.js:52-55`）：

```js
/* moves（内蔵技のID）と customMoves の両方。MOVES に無いIDは落とす */
(mon.moves || []).forEach(id => { if(MOVES[id]) ids.push(id); });
(mon.customMoves || []).forEach(cm => { ... });
```

`mon.customMoves[]` に**実体ごと**埋まっとる。棚（180本）は制作ツールにしか無くて、
個体に保存されるんは**選んだぶんだけ**。だから 128本を抱えた個体は構造的に生まれん。

**`learnable`（第4節）は容量のためやのうて、設計のためにやる** ——
「この四皇モンは何を覚えられるか」を決めるため。容量はもう解決しとる。

## 4. 覚える表（四皇モンごと）

今の creator には **「■ 覚える技（最大4つ）」**（`creator.tpl.html:224`）がある。
これは「**今なにを覚えとるか**」。にーくらが欲しいんは「**何を覚えられるか**」——別物。

四皇モンのデータに1つ足す：

```jsonc
{
  "name": "…", "stats": {…}, "types": [ … ],
  "moves": ["はっぱカッター", "…"],        // 今までどおり。今覚えとる技（最大4）
  "learnable": ["はっぱカッター", "つるのムチ", "ソーラービーム", … ]   // ★足す
}
```

- `learnable` が**無い**個体は、今までどおり**全部の `made` 技から選べる**（後方互換）。
- `learnable` が**ある**個体は、その中からしか「覚える技」に入れられん。
- creator の「覚える技」の区画に、候補を `learnable` で絞る動きを足す。
- 一覧から「覚えられる／覚えられん」を切る UI もそこに置く。

**`moves` は必ず `learnable` の部分集合**にする（`learnable` を狭めたとき、
既に覚えとる技が外れる場合は警告を出す。黙って消さん —— 掟9「黙って失敗するのが一番たちが悪い」）。

## 4.5 補助技（にーくら決定・2026-08-20「補助技も追加するべきだ」）

`aura` の3本（りゅうのまい・どくどく・うずしお）が**ダメージ0のまま**な件の決着。
generator で補助を判定しとるんをやめて、**技データで持つ**。

### 4.5-1. まず判定を技データへ移す

```js
/* 今（battle.tpl.html:1622）—— generator を見とる。これが元凶 */
const support = m.fx.generator==='aura';

/* あと —— 技データを見る。aura で攻撃技も作れるし、どの generator でも補助にできる */
const support = m.battle && m.battle.kind==='support';
```

これだけで **`aura` の攻撃技3本がダメージを取り戻す**（`applyHit` に到達するようになる）。
`kind` を書いとらん技は `attack` 扱い（後方互換）。

### 4.5-2. 補助の中身

```jsonc
"battle": {
  "type":"ドラゴン", "power":0, "cast":0.6, "cooldown":6.0, "range":"remote",
  "kind":"support",
  "effect": { "stat":"atk", "delta":+15, "dur":8.0, "target":"self" }
}
```

| キー | 取る値 | 意味 |
|---|---|---|
| `stat` | **`atk` / `def` / `eva` / `spd` の4つだけ** | **`hp` と `int` は対象外**（4.5-2b） |
| `delta` | −25〜+25 | 素の値への加算。素の値と合わせて **1〜100 に丸める** |
| `dur` | 3〜20 秒 | 試合中だけ。**試合をまたがん**（掟7「成長・周回要素を入れない」を守る） |
| `target` | `self` / `foe` | 自分に掛ける／相手に掛ける |

**同じ `stat` は重ねん。** 掛け直したら時間が延びるだけ（`delta` は加算せん）。
これが無いと、りゅうのまいを撃ち続けるだけで攻撃100になる。

### 4.5-2b. 試合中に動かせるステータスの整理（実測）

**「どこで読まれとるか」で動かせるかが決まる。** 全部の読み口を数えた（`battle.tpl.html`）。

| stat | 何に効くか（読み口） | いつ読まれるか | 補助技で動かす |
|---|---|---|---|
| **`atk`** 攻撃力 | ダメージ `power*(0.5+atk/100)` :1206<br>**相殺の押し勝ち** `owner.stats.atk*(1+tim)` :1732<br>**本演出の大きさ** `powerLevel` :1628 | その場 | **◎ 一番効く** |
| **`def`** 防御力 | 被ダメ `100/(100+def)` :1207<br>**ひるみ耐性** `flinchRate` :434 | その場 | **◎** |
| **`eva`** 回避力 | 回避の採点 `eva*0.62` :1840 | その場 | **○** |
| **`spd`** 素早さ | CD `cdScale` :431 ／ 溜め `castScale` :432 ／ 弾速 `shotScale` :433 | **技を撃つ瞬間に読んで固定** | **△ 条件付き** |
| **`int`** 賢さ | 読み `readOf` :1343 ／ 手の鋭さ `tempOf` :1427<br>**命令の聞き分け** `obedience` :1333 ／ 間の判断 :1526 | その場 | **× 除外**（にーくら決定） |
| **`hp`** 体力 | `maxHP = 40 + hp*1.6` :429 のみ | その場（getter） | **× 除外** |

**それぞれの中身：**

- **`atk` が一番おいしい。** 上げると**3つ同時に動く** —— ダメージが増え、相殺で押し勝つようになり、
  **弾が目に見えて大きくなる**（威力連動）。「積んだ」ことが画面で分かる。りゅうのまいの本命。
- **`def` は2つ動く。** 被ダメが減って、ひるみにくくなる。守りが素直に堅くなる。
- **`eva` は単純。** 回避の採点に足されるだけ。読みやすくて事故が無い。
- **`spd` は「次の技から」効く。** `f.cd[m.id]=m.cooldown*f.cdScale` は**撃った瞬間に計算して固定**されるけん、
  **今走っとる反動は縮まらん**。溜めも弾速も同じ。
  嘘やないけど「素早くなったのに動かん」に見えるけん、**UI と AIログで「次の技から」と言う**こと。
- **`int` は補助技の対象外**（にーくら決定・2026-08-20「賢さは補助技外にしよう」）。
  技術的には動かせるが、上げると読みは鋭くなる一方で**命令を聞かんくなり**（`obedience` が
  `- int/100*0.30`）、**手が読まれやすくなる**（`tempOf` が下がって選択が尖る）。
  掟16/23 が意図してそう作った「単純に上げても得やない」ステータスやけん、
  **補助技で動かす対象からは外す。** 賢さは個体の持ち味として据え置く。
- **`hp` は外す。** `maxHP` が getter やけん、動かすと**最大HPが伸び縮みしてゲージが跳ねる**
  （今 100/120 の個体が急に 100/144 になる）。回復とも混ざる。触らせん。

**補助技で動かせるのは `atk` / `def` / `eva` / `spd` の4つ。**
入れる順は `atk` → `def` → `eva`。`spd` は「次の技から効く」を UI と AIログで
説明できる形が出来てから足す。

### 4.5-2c. 先にやる下ごしらえ —— 読み口を1本に寄せる

ステータスは今**16か所で直に読まれとる**（`stats.atk` 等）。補助技の補正をここへ届けるには、
16か所を全部書き換えるか、**1本の関数に寄せる**か。後者しかない：

```js
/* 素の値 → 補助技の補正 → 特性の modifyStat（Phase 17）→ 1〜100 に丸め */
function statOf(f, key){ ... }
```

`get maxHP()` / `get cdScale()` / `damageOf()` / `readOf()` / `tempOf()` / 相殺の強さ /
回避の採点 —— 全部ここを通す。

**これをやらんと、特性を実装したとき補正系が2つになって競合する**（`docs/開発計画_v6.md` 4.3 の
`modifyStat(stat, value)` フック）。補助技の1手目はこの寄せ集めから。

⚠ 試合中にステータスを書き換える前例は既にある（`buildStatUI`、`battle.tpl.html:2137`）。
スライダで動かせて、`hp` だけ `f.hp=Math.min(f.hp,f.maxHP)` で丸めとる。
**この丸めの作法をそのまま使う。**

### 4.5-3. ⚠ ここが本題 —— AI が撃たんかったら意味が無い

**このゲームはプレイヤーが技を選ばん。** AI が `scoreMove()` で選ぶ。
その中身は**期待ダメージが軸**（`battle.tpl.html:1356`）：

```js
const dmg=damageOf(f,foe,m);
const dr=dmg/foe.maxHP;
const dmgV = dr/st*140;          // ← 威力0 の補助技は dr=0 → dmgV=0
T('期待ダメージ', dmgV);
T('手数',         (2.6/cd)*9);
T('発生の隙',     -cast*38);     // ← 溜めのぶんマイナス
```

**補助技は `power:0` やけん、期待ダメージ 0・発生の隙はマイナス。**
つまり今のまま補助技を足しても、**AI は一生撃たん**。データだけ増えて死ぬ。

だから補助技には**採点の項を足すのが本体**。案：

```js
if(m.battle && m.battle.kind==='support'){
  const e=m.battle.effect;
  /* 何秒ぶんの得か = 効果の大きさ × 残っとる時間のうち効いとる割合。
     既に同じ強化が乗っとるなら値打ちは落ちる（重ね掛けを防ぐ） */
  const already = hasBuff(f, e.stat) ? 0.15 : 1.0;
  T('補助の値打ち', buffValue(f,foe,e) * already);
}
```

**`buffValue` の考え方**：`atk+15` なら、その個体が `dur` 秒で撃てる技の
期待ダメージがどれだけ増えるかを実際に見積もる（＝攻撃技と同じ物差しに乗せる）。
そうすれば「今は殴った方が得」「ここは積んだ方が得」をAIが自分で判断できる。

**AIログに項として出す**（掟9「内訳が見えん実装をしない」）。
出さんかったら「なんで今りゅうのまいを撃ったんか」が一生分からん。

### 4.5-4. ビルドツール側

にーくら「もちろん、ビルドツールもそれに対応させる」。

- 制作ツールの戦闘値の区画に **`kind`（攻撃／補助）の切り替え**
- `補助` を選んだら `effect`（どのステータス・いくつ・何秒・誰に）の入力が出る
- `攻撃` のときは `effect` の入力を出さん
- 補助を選んだら**威力の入力を伏せる**（0固定。使わん値を見せたら混乱する）

### 4.5-5. 特性（Phase 17）とぶつからんか

`docs/開発計画_v6.md` 4.3 が特性のフックを**9個に固定**しとって、その中に
`modifyStat(stat, value)`（ステータス参照時の常時補正）がある。

補助技の効果も**同じ「ステータスに補正を掛ける」入口を通す**べき。
別々に作ると、特性を実装したとき2つの補正系が競合する。
`f.stats.atk` を直に読んどる箇所を**1本の関数に寄せる**のが先。
これは補助技を作るときの下ごしらえとして必ずやる。

### 4.5-6. 規模の話

補助技は**データやのうて仕組み**やけん、`quick` では収まらん。触る所：

技データの形 / `launch()` の support 判定 / ステータス参照の一本化 /
効果の適用と時間切れ / `scoreMove` の採点項 / AIログ / 制作ツールのUI / 回帰ゲート

**これは1フェーズぶん。** 整理（第5節の1〜4）とは別に立てる。

## 6. 回帰ゲート

1〜4 はデータと構造をいじるけん、**壊れても絵に出らん**のが怖い。
`tools/verify_movelist.js` を作って数える：

1. `dist/*.html` を `file://` で開いて、**技が0本になっとらん**（第2節の事故の再発防止）
2. `dist/` の技数 == `library.json` の `status:"made"` の数
3. レコードの必須が status ごとに満たされとる：
   - `made` … `name` / `fx` / `battle.type` / `battle.power` / `battle.cast` / `battle.cooldown`
   - `idea` … `name` / `battle.type` だけ。**`fx` も威力も無くてよい**
     （ネタ帳の表は「技名・作り方・パレット・ねらい」しか持っとらん。

     いい加減な数字を入れる方が危ない —— 決めたのか未定なのか見分けが付かんくなる）
4. 亜空切断・灼熱弾・Codex の14本が**1本も欠けとらん**
5. `learnable` を持つ個体で、`moves ⊆ learnable` が成り立っとる
