## 1. ゲームの基本思想

「ポケット四皇モンスター」は、仲良しグループ「四皇」を題材にした、収集・育成・AI自動戦闘ゲーム。

中心となるループは、

```
捕獲 → 育成 → 編成 → AI戦闘 → 再育成
```

### 1.1 目指す戦闘像（最重要）

**目標は「ゲーム版ポケモン」ではなく「アニメ版ポケモン」の戦闘である。**

既存のターン制RPGの戦闘が退屈になる原因は2つ。

1. 相互に技を撃ち合うだけで、技同士が干渉しない
2. 1発の威力が高すぎて2〜3ターンで決着する

本作はこれを次の4要素で解決する。

| 要素 | 実現方法 |
|---|---|
| 避ける | 視覚的回避システム（12章） |
| **技と技がぶつかる** | **相殺システム（11章）** |
| 攻撃中に割り込まれる | 攻撃準備時間を持つリアルタイム戦闘（8章） |
| 指示のタイミングが勝敗を決める | クォーター制＋タイムアウト（9章） |

### 1.2 設計原則

**(a) 少ないステータスで多くを語る**
ステータスは6つしか存在しない。増やさない。その代わり1つが複数の意味を持つ。

**(b) タイプ相性表を作らない**
タイプはポケモンの18種をそのまま使うが、**相性による有利不利は存在しない**（15.1）。
勝敗は編成の相性ではなく、プレイヤーの采配で決まる。

**(c) プレイヤーの編成を制限しない**
コスト上限で編成を縛らない。**誰でも最強の6体を並べてよい。**
その代わり、強い個体を失った時の損失が大きい（18章）。

**(d) プレイヤーの時間を奪わない**
レベル上げ作業は存在しない。**周回して数値を伸ばす成長要素も実装しない。**
強くなるのは「捕獲」と「育成の配分」であって、「時間をかけること」ではない。

**(e) 全員ができることはルールにしない**
特定の状況が有利になる仕組み（例：土壇場での強化）をルールとして全体に配ると、
全員がその状況を狙い始めて戦術が単一化する。
**そういうものは特性として一部の個体だけに配る。**

## 2. 技術方針

### 2.1 実行環境

- **Web（ブラウザ）+ Canvas 2D**
- 静的ホスティングで配布し、URL共有できること
- **スマートフォン（Android Chrome）を第一ターゲット**。縦持ち、タッチ操作前提
- 内部解像度 **384×288**、ニアレストネイバー拡大（ドット感を保つ）

### 2.2 ファイル構成

- **ES Modules による責務分割を必須とする。巨大な単一ファイルは禁止**
- 技ラボとバトルは**同一の `EffectSystem.js` を共有する**（別々に書いてはならない）

### 2.3 保存

- **SaveSystem は IndexedDB を前提に設計する**
- 四皇モンごとに画像3枚＋音声1つを登録するため、localStorage では容量が破綻する

### 2.4 決定論（重要）

- 戦闘ループは **固定タイムステップ**（`dt = 1/60` 秒固定）
- 乱数はすべて **シード付き擬似乱数（PRNG）** を経由する。`Math.random()` の直接呼び出しは禁止
- **同じシード＋同じ入力なら、同じ試合が完全に再現できること**

## 3. ステータス

### 3.1 6つのステータス

**ステータスはこの6つのみ。追加してはならない。**

| ステータス | 主な意味 | 副次的な意味 |
|---|---|---|
| **攻撃力** | 与ダメージ | **相殺の押し勝ち**（11章） |
| **防御力** | 被ダメージ軽減 | **ひるみ耐性**（被弾しても技を撃ち切る） |
| **体力** | 最大HP | 長期戦での粘り |
| **素早さ** | 行動間隔の短さ | 自分の飛翔体の速度 |
| **回避力** | 回避の成功率 | — |
| **賢さ** | **AI判断の精度**（10章） | **状況を読む力**・命令の効きにくさ・読まれやすさ |

数値レンジは 1〜100、標準を 50 とする。

### 3.2 素早さと回避力を分けている理由

リアルタイム戦闘では単一の「速度」が行動回数・先手・回避の三重に効き、速度一強になる。
**「素早さ（撃つ頻度）」と「回避力（避ける能力）」を別ステータスにすることで構造的に解決している。**
両者を後から混ぜてはならない。

### 3.3 防御力と回避力の非対称性

| | 性質 |
|---|---|
| 防御力 | 食らうが減らす。**安定**。単体で機能する |
| 回避力 | 食らわないか丸ごと食らうか。**博打**。**賢さがないと機能しない** |

### 3.4 攻撃力の交換レートに関する注意

攻撃力は「ダメージ」と「相殺の勝敗」の二重の意味を持つため素の価値が高い。
**`stat_tradeoff_config` において攻撃力+1のコストを他より重めに設定すること。**

## 4. 特性（Ability）

### 4.1 概要

四皇モンは**特性を最大1つ持つ**（持たない個体もいる）。
特性は常時発動する受動能力であり、技とは別物である。

### 4.2 設計原則（最重要）

> **特性は「数値を変えるもの」より「ルールを変えるもの」を優先する。**

数値を変えるだけの特性（例：攻撃力+10%）は、実質ただの隠しステータスになる。
それは6ステータスで表現できるため、特性にする価値がない。

**本作で最も価値があるのは、AI判断と命令の層に介入する特性である。**

### 4.3 実装：9つのフックに固定する

技エフェクトはデータ駆動にできるが、**特性はルールを変えるためコードが必要**である。
無制限にコードが増えるのを防ぐため、**フックの種類を以下の9個に固定する。**

| フック | 呼ばれるタイミング |
|---|---|
| `onBattleStart` | 試合開始時 |
| `onQuarterStart` | 各クォーター開始時 |
| `modifyStat(stat, value)` | ステータス参照時（常時補正） |
| `modifyMoveScore(move, ctx)` | AIが技を評価する時 |
| `onOrder(order)` | プレイヤーの命令を受けた時 |
| `onDamaged(dmg, attacker)` | 被弾時 |
| `onClash(mine, theirs)` | 相殺が起きた時 |
| `onDodge(success)` | 回避判定の直後 |
| `onFaint()` | 死亡時 |

**どの特性も、この中の1〜2個に小さな関数を刺すだけで実装すること。**
新しいフックを増やす場合は、既存の特性で代用できないか必ず先に検討する。

特性の**数値部分は外部データに置く**（効果量をコードへ直書きしない）。

### 4.4 初期の特性リスト（叩き台）

**【命令・AI系】** — 本作固有で最も価値がある領域

| 特性 | 効果 |
|---|---|
| **以心伝心** | 賢さに関係なく命令が最大限効く。賢さの弱点を1つ消す |
| **天邪鬼** | 命令と逆の行動を取りやすい。ただし通った時は威力が上がる |
| **読心** | 相手の賢さを無視して行動を読む。回避と迎撃の精度が跳ね上がる |
| **唯我独尊** | 命令を一切受け付けない。代わりに全ステータスが上がる |

**【戦闘構造系】**

| 特性 | 効果 |
|---|---|
| **馬鹿の一つ覚え** | 同じ技を連続で使うほど威力が上がる |
| **弾き返し** | 相殺スコアが大きく上がる。飛び道具を撃ち落とす専門家 |
| **鉄壁** | ひるまない。殴られながらでも必ず技を撃ち切る |

**【クォーター系】**

| 特性 | 効果 |
|---|---|
| **後半型** | クォーターが進むほど強くなる |
| **先手必勝** | 第1クォーターの間だけ大幅強化 |

**【死亡・土壇場系】**

| 特性 | 効果 |
|---|---|
| **不屈** | 一度だけHP1で耐える |
| **形見** | 自分が死ぬと、残った味方全体が強化される |
| **身代わり** | 味方が致命傷を受ける時、代わりに倒れる |
| **背水の陣** | **所持コストが残りわずかな時、大幅に強化される** |

> **背水の陣は特性としてのみ存在させる（原則 1.2(e)）。**
> これを全体ルールにすると、全員がわざと追い詰められるのを狙い始めて戦術が単一化する。

### 4.5 コストへの影響

**特性はコストに大きく効かせること。**
そうしないと、自作四皇モンで強力な特性を選び放題になる。

## 5. 伸びしろ

### 5.1 レベルは存在しない

四皇モンは最初から6つのステータスを持つ。これがその個体本来の能力である。

### 5.2 伸びしろ

伸びしろポイントは能力を全部上げるものではなく、**能力配分を変形させる行為**とする。

```
素早さ +2 / 防御力 -0.5
```

**交換ルールをコードへ直書きしてはならない。** `stat_tradeoff_config` に置く。

### 5.3 特化ペナルティ

極端な特化には代償を増やす。

```
軽い特化：素早さ +2 / 防御力 -0.5
極端な特化：素早さ +2 / 防御力 -1.0
```

## 7. 性格

性格は「AI判断の重み付け」として作用する。**分岐で書かない。**
初期実装は 好戦性 / 慎重性 / 忠実性 / 自己保存性 の4つ程度に留める。

### 賢さ × 忠実性

| | 忠実性 高 | 忠実性 低 |
|---|---|---|
| **賢さ 高** | 命令を賢く解釈して実行する（最も強い） | 勝手にやる。ただし強い |
| **賢さ 低** | 言われた通りにしかできないが素直 | 手に負えない |

## 8. 戦闘システム

### 8.1 リアルタイム

各四皇モンは独立して以下を繰り返す。ターン制ではない。

```
AI判断 → 行動決定 → 攻撃準備 → 攻撃 → クールダウン → 再判断
```

各個体は `actionTimer` / `cooldownTimer` / `animationTimer` を独立して持つ。
行動間隔は**素早さ**から算出する。

### 8.2 クォーター制

| 項目 | 初期値 |
|---|---|
| 1クォーターの長さ | 30秒 |
| インターバル | 10秒 |
| クォーター数 | 上限なし（決着まで繰り返す） |

- **インターバル中は戦闘が完全に停止する**
- インターバル中にできること：作戦変更、交代

### 8.3 威力と体力の比率（重要）

```
標準的な技1発のダメージ = 相手最大HPの 12〜20%
```

**一撃必殺技、および急所による即死は実装しない。**

### 8.4 ひるみ

被弾時、**防御力**に応じて攻撃準備が中断されることがある。

### 8.5 長期戦対策

| クォーター | 与ダメージ補正 |
|---|---|
| 1〜4Q | ×1.00 |
| 5〜6Q | ×1.10 |
| 7Q〜 | ×1.25 |

## 9. 命令システム

プレイヤーは技を直接選択しない。命令は**2層**に分かれる。

### 9.1 作戦（インターバルで設定・そのクォーター中ずっと有効）

攻撃重視 / 慎重に戦え / 回避優先 / 温存

実装：AIの評価スコアにかかる**持続的な加点**。

### 9.2 指示（タイムアウト・即時発動）

| 項目 | 初期値 |
|---|---|
| 回数 | **1クォーターにつき1回** |
| 持ち越し | **不可** |
| 効果時間 | 数秒間 |
| 演出 | 発動時に一瞬スローモーション |

大技を狙え / 退け / **迎え撃て** / 交代

実装：評価スコアへ**一時的に乗る大きな加点**。作戦とは別レイヤー。

### 9.3 命令の従いやすさ

- **忠実性**が低い個体は、そもそも従う気がない
- **賢さ**が高い個体は自分の判断を優先するため、命令の加点が順位を覆しにくい
- **タイムアウトによる指示は加点が大きく**、一時的に従いやすくなる
- 特性 **以心伝心 / 天邪鬼 / 唯我独尊** がここに介入する

**完全なランダム無視にはしない。必ずスコアの重み付けとして処理する。**

### 9.4 采配のための情報開示（必須）

属性相性表が存在しない以上、**プレイヤーは画面から采配の材料を読み取れなければならない。**

- **相手の攻撃準備インジケータ**
- **相手のクールダウン残量**
- 相手個体の性格の傾向（曖昧な表示でよい）
- **両陣営の所持コストバー**（18章）

## 10. 賢さと判断

### 10.1 賢さとは何か

他の5つは**「実行」**の能力。**賢さだけが「判断」の能力**であり、他の5つの発揮効率として作用する。

- 回避力90・賢さ20 → 避ける能力はあるが、**避けるべき瞬間が分からず当たる**
- 攻撃力90・賢さ20 → 強いが、**無駄なタイミングで大技を撃つ**

### 10.2 実装：選択のブレ幅

```
温度 T = f(賢さ)   ※ 賢さが高いほど T は小さい
選択確率 = softmax(スコア / T)
```

**実装はこれだけでよい。分岐を増やしてはならない。**

### 10.3 賢さが裏目に出る構造（重要）

**賢さは一方的に有利であってはならない。** 上記の実装から以下が自動的に生じる。

**(a) 読まれる** — 賢い個体は最善手に寄るため行動が予測可能。逆に賢さの低い個体はどんな相手にも読めない。

**(b) 命令が効きにくい** — T が小さいため、加点しても順位が覆りにくい。

**(c) 手堅くなる** — リスク評価が正確な分、勝負手を打たない。

### 10.3b 賢さのもう1つの役割：状況を読む（重要）

> **賢さとは「いかに既存の条件をうまく使えるか」である。**

賢さは選択のブレ幅（温度）だけではない。
**AIの評価項目を2種類に分け、片方を賢さで減衰させる。**

| 種類 | 内容 | 賢さの影響 |
|---|---|---|
| **基本項** | 誰でも分かること | なし |
| **読み項** | 状況を読めた個体だけが得る加点 | **賢さに比例して減衰** |

```
読み精度 read = 賢さ / 100
読み項の値 = 素の値 × read
```

**基本項**：期待ダメージ / タイプ一致 / 手数 / 発生の隙 / とどめ / 被弾リスク / 手癖

**読み項**：

| 項目 | 発生条件 |
|---|---|
| **好機** | 相手が溜め中・クールダウン中・硬直中。安全に大技を溜められる |
| **割り込み** | 相手の溜め時間より自分の発生が速い。先に殴れる |
| **迎撃機会** | 敵の飛翔体が飛来中で、迎撃向きの技を持っている |
| **あと一歩** | あと少しで倒せる状況 |
| **過剰** | 相手の残HPに対して威力が過剰 |

**この設計の効果（実測）**

溜めの長い大技（落雷：発生の隙 -22.4）は、素の評価では常に負けて死に技になっていた。
読み項を導入した結果：

- 賢さ95 → `好機 +18.1` が入り、**相手の硬直を狙って意図的に撃つ**
- 賢さ8 → `好機 +1.5` しか得られず、**撃つ時はただのブレ**

**技のバランスを変えずに解決した。**
「強い技が選ばれない」問題の多くは、技が悪いのではなくAIが状況を読めていないだけである。
係数をいじる前に、まず読み項で解けないか検討すること。

なお読み項が増えるほど、賢い個体の行動はより状況依存＝**より予測可能**になる。
10.3(a) の不利益は、読み項を足すたびに強まる。

### 10.4 相手の行動予測

```
予測精度 = 自分の賢さ × 相手の賢さ（＝相手の予測されやすさ）
```

特性 **読心** はこの式の「相手の賢さ」を最大値として扱う。

## 11. 相殺システム

### 11.1 概要

**飛翔中の projectile 同士が接触した場合、相互作用を発生させる。**
ターン制では原理的に実装できない、本作固有の表現である。

### 11.2 判定

```
相殺スコア = 攻撃力 × (1 + タイミング補正)

タイミング補正の範囲： 早撃ち +0.4 〜 不意打ち -0.4
```

補正の幅は攻撃力の差より小さく設定する。したがって、

- **攻撃力が大きく上回っていれば、采配ミスでも相殺に勝てる**
- **攻撃力が拮抗している時だけ、采配が結果を決める**

補正の幅（初期値 ±0.4）は外部設定とし、**「強さで殴るか、腕でカバーするか」の線引きをこの1つの数値で調整できる**ようにする。

特性 **弾き返し** はこのスコアに介入する（`onClash`）。

### 11.3 結果の3分岐

| スコア差 | 結果 |
|---|---|
| 小 | `cancel` 相殺。両方消滅し、接触点で爆発 |
| 中 | `prevail` 勝った側が威力を減衰させて飛行を継続 |
| 大 | `pierce` 貫通。勝った側は減衰せず継続 |

### 11.4 属性について

**属性による優劣は存在しない。** 属性は見た目・分類のためのラベルである。

### 11.5 采配の二択

| 命令 | 適する個体 | 性質 |
|---|---|---|
| **避けろ** | 回避力型 | ノーダメージ。ただし賢さが要る。外すと丸ごと食らう |
| **迎え撃て** | 攻撃力型 | 確実。ただし撃ち返す1発を消費する |

### 11.6 実装範囲

**初期実装は projectile 同士のみ。** beam / slash / lightning との相互作用は後回し。

## 12. 回避

```
敵が発射 → 味方AIが回避判断 → 味方画像が横方向へ移動
 → 弾が元の位置を通過 → 元の位置へ戻る
```

- 自由移動フィールドは使用しない。固定構図の中で画像位置を一時的に変化させる
- **回避力**が成功率を、**賢さ**が「避けるべき瞬間の見極め」を決める
- 相手の**素早さ**（飛翔体の速度）が高いほど難しくなる

## 13. アニメーション

キャラクター画像は `normal` / `attack` / `hurt` の3枚のみ。
**画像自体にアニメーションを要求しない。**

動きはすべてゲーム側の変形処理で行う。

### 実装済みの原則（守ること）

- **足元を基準に拡縮する。** 中心基準にすると、つぶれた時に足が地面にめり込む
- **面積を保存する。** 縦に伸びる時は必ず横が縮む（squash & stretch）
- **影を連動させる。** 跳ぶと影が小さく薄くなることで高さが伝わる
- **ジャンプと飛行は別物。** ジャンプは画面内、飛行は画面外へ抜けて一度消える

## 14. 技エフェクト

### 14.1 大原則

**画像生成AIを使用しない。技のドットエフェクトはゲーム自身がコードで生成する。**
**技ごとに専用アニメーションコードを書いてはならない。**

### 14.2 generator の種類

`projectile` / `beam` / `slash` / `lightning` / `aura` / `explosion`

技は「設計情報（JSON）」だけを持ち、描画は Effect Generator が行う。

### 14.3 画面演出（背景変化）

**画面演出も技データの一部である。** 技ごとに指定する。

| 種類 | 内容 |
|---|---|
| `flash` | 画面全体が一瞬光る |
| `blink` | 背景が指定回数点滅する |
| `tint` | 背景全体に色が乗る |
| `darken` | 背景が暗くなる（溜め演出） |
| `shake` | 画面が揺れる |
| `lines` | 走査線／集中線（横・縦） |

**タイミングを `cast`（技を出した時）と `impact`（当たった時）で個別に指定できること。**
これにより「溜めで暗転 → 直撃で白飛び」のような二段構えが作れる。

### 14.4 シード

生成エフェクトは `effectSeed` を持つ。
**同じ技であれば、ゲームを再起動しても同じ見た目が再現されること。**

## 15. 技システム

### 15.1 タイプ（分類）

**ポケモンの18タイプをそのまま使用する。**

ノーマル / ほのお / みず / でんき / くさ / こおり / かくとう / どく / じめん /
ひこう / エスパー / むし / いわ / ゴースト / ドラゴン / あく / はがね / フェアリー

- 四皇モンは**最大2つ**のタイプを持つ
- 技は**1つ**のタイプを持つ
- **タイプ相性表は作らない。** 有利不利は一切存在しない

**唯一の効果はタイプ一致ボーナスである。**

```
技のタイプが使用者のタイプのいずれかと一致 → ダメージ × STAB
STAB 初期値 = 1.25
```

AIのログでは、期待ダメージと**タイプ一致を別項目として表示すること**。
どれだけ効いているかが見えないと調整できない。

### 15.2 技のパラメータ

| 項目 | 内容 |
|---|---|
| 威力 | ダメージ倍率 |
| タイプ | 18種から1つ（**優劣なし。一致ボーナスのみ**） |
| 発生時間 | 準備にかかる時間 |
| クールダウン | 再使用までの時間 |
| 命中 | 基礎命中率 |
| AIタグ | 判断用ラベル |
| エフェクト設定 | generator への指示（14章） |
| 画面演出 | screen ブロック（14.3） |

飛翔体の速度は技ではなく、**撃った個体の素早さ**から算出する。

AIタグ例：近距離向き / 遠距離向き / 高威力 / 低リスク / とどめ向き / 回避されやすい / 連発向き / 瀕死時危険 / 迎撃向き

## 18. コスト経済（本作の中核仕様）

### 18.1 コストとは何か

コストは「編成の枠」ではなく、**陣営の体力**である。

各プレイヤーは試合開始時に **所持コスト** を持つ。

| 項目 | 初期値 |
|---|---|
| 所持コストの初期値 | **150**（両陣営とも同じ） |
| 所持コストの上限 | 初期値の2倍（300） |

### 18.2 コストの増減

```
味方が死ぬ   → 所持コスト −（その四皇モンのコスト全額）

敵を倒す     → 所持コスト ＋（倒した相手のコスト
                              × min(比率上限, 相手のコスト ÷ 倒した個体のコスト)
                              × 係数k）
```

| 定数 | 初期値 |
|---|---|
| 係数 k | 0.5 |
| 比率上限 | 2.0 |

### 18.3 計算例（実装確認用）

| 状況 | 計算 | 獲得 |
|---|---|---|
| コスト20が コスト140を倒す | 140 × min(2.0, 7.00) × 0.5 | **+140** |
| コスト50が コスト50を倒す | 50 × min(2.0, 1.00) × 0.5 | **+25** |
| コスト140が コスト20を倒す | 20 × min(2.0, 0.14) × 0.5 | **+1.4** |

**格上を食うほど大きく増え、格下を潰してもほとんど増えない。**

### 18.4 この設計が生むもの

**(a) 銀河軍団を誰も止めない。ただし経済が悪い**

コスト140を6体並べてよい。ただし、

- 1体でも落ちれば所持コスト150が10になり、次の1体で敗北
- 格下を何体倒してもコストがほとんど増えない

**(b) 弱い四皇モンに3つの明確な役目ができる**

| 役目 | 内容 |
|---|---|
| **刺客** | 捨てるつもりで格上に刺しにいく。負けても損失は小さく、勝てば盤面がひっくり返る |
| **削り役** | 倒しきらなくてよい。半分削って死ねば十分な仕事。損失は小さく、その後エースが仕留めて大きく獲得する |
| **偵察** | 先に出して相手の技・性格・AIの癖を見る。安い個体ほど気軽に出せる＝情報が安く買える |

**(c) 同じルールから、非対称な2つの遊び方が生まれる**

| 編成 | やっているゲーム |
|---|---|
| 高コスト編成 | **「1体も落とさない」ゲーム** — 交代と引き際の判断が命綱 |
| 低コスト編成 | **「1体だけ食う」ゲーム** — 全部捨ててでも1回刺す |

**強い側は守りのゲーム、弱い側は攻めのゲーム。** これが本作の戦略の核である。

### 18.5 CostCalculator の重要度（警告）

コストは**損失額と獲得額の両方**を決めるようになった。

もしある四皇モンのコストが不当に安く見積もられていた場合、その個体は
「強い」と「死んでも痛くない」と「刺客ボーナスが大きい」を**三重取り**する。確実に壊れる。

- `CostCalculator` は独立モジュールとし、式を差し替えられるようにする
- **仮の式でよいので早い段階で入れ、実戦で検証する**（フェーズを前倒しする理由）
- 考慮対象：6ステータス / 伸びしろ配分 / 技性能 / **特性** / 性格上の有利要素
- **賢さは有利にも不利にも働くため、単純な線形評価は適さない**

### 18.6 UI

**所持コストバーを画面上部に敵味方2本表示する。**

四皇モンが死んだ瞬間、鳴き声が0.7倍速で鳴り、**コストバーがガクッと落ちる**。
残りが少なくなったら赤く点滅する。

**この試合で最も緊張する瞬間になるため、演出に手を抜かないこと。**

## 19. 死亡

## 23.5 音（サウンド）

### 責務分担（本作の原則）

| 誰が | 何を決めるか |
|---|---|
| **鴨川** | **鳴る音そのものと、鳴らすタイミング。例外なく全部** |
| コード生成AI | 見た目の演出、音を鳴らす「口」の実装 |

音を仕様として文書に固定しない。**音ラボの設定JSONが唯一の正解**とする。

### 23.5.1 音バンク

CC0素材79音を11カテゴリ（発射・弾／光線／大砲・重火力／爆発・着弾／斬撃／
金属・相殺／打撃・近接／被弾／断末魔／魔法・電撃・空間／UI・システム）へ分類し、
モノラル22kHzへ再圧縮したうえで data URI としてHTMLへ焼き込む。外部ファイル参照はしない。
ユーザーが自分の音声ファイルを足すこともでき、追加音は設定JSONに同梱されて配布される。

### 23.5.2 音の割り当て層（audio_config）

技の音は「タイミング」と「ずらし秒数」の2つだけで表す。

```
AUDIO_CFG.moves[技ID] = [ { id:音ID, at:'cast'|'fire'|'impact', off:秒, vol:0-1.5, rate:0.4-2 }, ... ]
AUDIO_CFG.system[イベントID] = { id:音ID, off, vol, rate }
```

- `cast` … 技を出すと決めた瞬間（溜めの始まり）
- `fire` … 弾が出る・刃を振り抜く瞬間
- `impact` … 着弾した瞬間
- `off` … その瞬間から何秒あとに鳴らすか（**同じ瞬間に複数の音を重ねられる**）

再生時は `SPEED.battle`（0.75倍）でオフセットが引き伸ばされる。演出が遅くなれば音も一緒にずれる。

システムイベントは15種：タブ／作戦決定／指示／交代／指示画面開閉／
クォーター開始・終了／被弾／ひるみ／戦闘不能／回避／相殺／貫通／勝利／敗北。

### 23.5.3 禁止

- コード内に音IDをベタ書きしない。必ず `playSys()` / `playMovePhase()` を通す
- 音の再生を戦闘の乱数・状態へ影響させない（**決定論チェックが通らなくなる**）

# コード生成AIへの禁止事項

1. 最初から全機能を一括実装しない
2. ゲームロジックと描画を密結合させない
3. 能力・コスト・捕獲難易度などの数値をコードへ大量に直書きしない
4. 技ごとに専用アニメーションコードを書かない
5. 技エフェクト用画像を外部生成AIへ依存しない
6. 自作四皇モンを直接手持ちへ追加できる抜け道を作らない
7. ターン制戦闘へ変更しない
8. プレイヤーへ毎回の技選択を要求しない
9. `Math.random()` を直接呼ばない。必ずシード付きPRNGを経由する
10. 可変 delta time を戦闘計算へ使わない
11. AIログの実装を後回しにしない
12. 一撃必殺・急所即死を実装しない
13. ステータスを6つより増やさない
14. **タイプ相性表を作らない**（一致ボーナスのみ）
15. 素早さと回避力を1つのステータスにまとめない
16. 賢さを「高いほど強い」だけの能力にしない。10.3の3つの不利益を必ず実装する
17. **コスト上限で編成を制限しない**
18. **周回して数値を伸ばす成長要素を実装しない（プレイヤーの時間を奪わない）**
19. **土壇場ボーナスを全体ルールにしない。特性としてのみ実装する**
20. **特性のフックを9個より増やさない。増やす前に既存フックでの代用を必ず検討する**
21. **特性を「数値を変えるだけ」のものばかりにしない**
22. **技ラボとバトルで EffectSystem を別々に実装しない**
23. **賢さを「選択のブレ幅」だけの実装で済ませない。10.3b の読み項を必ず実装する**
24. **AIの評価項目を、内訳が見えない形（合計値だけ）で実装しない**
25. **音IDをコードへベタ書きしない。音の決定権は鴨川にあり、コードは `playSys()` / `playMovePhase()` を呼ぶだけ**
26. **音の再生を戦闘ロジック（乱数・状態）へ影響させない**
